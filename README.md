# PSD 到 Unity UI

面向 Codex 的 PSD/PSB → Unity UGUI 工作流 Skill。支持首次制作、人工修正整理稿后续作，以及已有 PSD、Prefab、绑定代码的持续维护。

本仓库提供执行规则、溯源模板和只读图层检查脚本。PSD 编辑、Prefab 导出和代码绑定复用目标环境的现有工具；它不是独立的 PSD 转换器，也没有后台文件监听或通用自动合并器。

已有正式 Prefab 的日常维护默认只导出图片：更新并核验固定 `_UI` → 现成工具 `Export Images` → 第三份 MD 资源处理 → 回读现有 Prefab 图片引用与显示。不重生成 Prefab，不强制重做减法或绑定，不提交空的 Prefab 审核。首次制作或用户明确批准重生成时才走完整 Prefab 链路。

白、蓝、紫、橙等已知品质图片在 `_UI` 阶段先按确认的编号映射命名，例如 `Quality_1` 至 `Quality_4`；`Quality_c` 是另一个运行时 Image 控件的绑定名，不是图片名。第三份 MD 核验实际导出及引用，不重复做这组图片的初次命名。

需要生成时，两步生成入口是硬性约束：**`_UI.psd / _UI.psb → Prefab` 必须走项目现成 PSD 工具，`Prefab → 代码与绑定` 必须走项目现成 UI 生成/刷新工具。** PLink 的 Unity/Prefab/Assets 自动化只能调用 Coplay MCP 的直接工具或请求载荷，不得另写生成器、拼接底层导出服务、手写生成结果或以外部脚本文件承载 Unity 资源操作。PSD 编辑和烘焙可使用 Photoshop 或其外部自动化，但只能作用于固定 `_UI` 工作稿并保留源稿、备份和重开核验边界。非文字图片的已启用描边/阴影须在导出前连同 Fill/Opacity 烘焙进独立切图像素，并核验透明边界；文字效果仍按现有 Prefab 能力处理。输出沿用当前工具配置及已确认参数，工具失败时报告实际状态，文件还原由用户处理，不自行生成替代产物。

版本号见 [VERSION](VERSION)，发布记录见 [CHANGELOG.md](CHANGELOG.md)。Git 标签使用 `vX.Y.Z`。

## 安装与版本维护

需要 Python 3、Git 和按项目入口读取 Skill 的 Agent 环境。Skill 作为普通目录安装到项目 `.aiworkflow/skills/plink-psd-to-unity-ui`，由项目自己的版本控制管理；安装目录不保留嵌套 `.git`。首次获取可在项目外临时克隆后复制除 `.git` 外的内容，也可从正式发布包安装。

仓库访问需要相应的 GitHub 权限。安装后核对项目 `AGENTS.md` 或等效入口能否路由并读取本 Skill；`$plink-psd-to-unity-ui` 表示调用意图，是否被客户端原生识别取决于安装环境，实际读取以项目入口为准。维护者在独立 Git 工作副本中发布版本，项目内安装副本通过随附脚本检查和更新。不要把客户端配置、凭据、第三方依赖或项目美术资源放入 Skill。

## 调用时自动检查更新

开始一项 PSD/UI 任务时，Agent 先检查本仓库 `main` 中的版本号：

- 没有更高版本：继续使用本地 Skill。
- 有新版：提示本地版本、新版本和变化；选择更新后由 Agent 自动更新到已展示的提交，再读取新规则继续任务。当前会话已明确允许本次自动更新时不重复询问。
- 拒绝更新：本次任务使用现有版本，后续阶段不重复提示。
- 网络不可用、本地有修改或历史分叉：说明原因并保留本地文件，继续现有版本，不自动丢弃修改。

这由 Skill 指令和随附脚本在调用时执行，需要可用的 Python 3、Git 和仓库访问权限；不是 Codex 后台更新服务。首次上传的无版本号旧版需要先手动更新一次，才能获得此入口。

脚本可手动调用；更新命令只在已决定更新时运行：

```powershell
$skillPath = '<项目/.aiworkflow/skills/plink-psd-to-unity-ui 的实际路径>'
python (Join-Path $skillPath 'scripts/skill_update.py') check
python (Join-Path $skillPath 'scripts/skill_update.py') update --target-commit '<检查返回的target_commit>'
```

`check` 不改工作文件；`update` 在系统临时目录获取远端，逐文件核对当前版本标签后安装用户确认的提交，安装目录始终不创建 `.git`。存在本地修改或无法取得可信版本基线时停止更新并保留现状。更新后 Agent 重新读取当前任务所需规则；交付时注明实际执行版本。详细条件见 [版本检查与更新](references/version-updates.md)。

维护者发布新版本时，同一提交更新 VERSION、CHANGELOG.md 和实际内容，推送 `main` 后在该提交创建 `vX.Y.Z` 标签，并用 `git push origin vX.Y.Z` 推送标签、核对远端指向。已有标签不移动；版本号未升高的提交不会触发更新提示。

## 如何使用

完整制作：

```text
使用 $plink-psd-to-unity-ui，把指定 PSD 整理为 750×1334，调用项目已有工具输出 Prefab。
按已明确的范围完成减法、布局、适配、绑定及已有功能维护，未决冲突单独说明。
工程内不新增流程辅助脚本。
```

常见维护请求：

| 目标 | 示例 |
|---|---|
| 只整理 PSD | 使用 $plink-psd-to-unity-ui，本次只整理这份 PSD，不生成 Prefab。 |
| 继续人工修正版 | 我改了 `_UI.psd`，以这份修正版继续导出，更新原修改说明。 |
| 更新已有界面 | 用新的源 PSD 更新现有界面，先对比源稿、固定 `_UI` 与当前说明，提交差异让我审核；同意后默认仅导出图片并走第三份 MD；整体大改时询问是否重生成 Prefab。 |
| 记录适配修正 | 我改了正式 Prefab 的适配，检查显示并维护原修改说明。 |
| 仅改功能代码 | 只修改这个按钮的点击逻辑，沿用现有有效绑定。 |

提供源文件与项目位置，并说明本次需要完成的阶段。模块名、面板名和设备范围能从项目可靠推断时会沿用；业务行为以明确需求为准。

## 完整流程

本节仅适用于首次制作或用户批准重生成；已有日常维护使用前述图片路径，不重跑本节减法及绑定。

1. **保留源文件并整理 PSD。** 默认设计画布为 750×1334，另存 `<原名>_UI.psd`；已有对应整理稿时先备份旧版，再更新固定工作稿，PSB 保留扩展名。先结合结构、画面、需求和已有记录识别运行时互斥/条件状态；源 PSD 中自身或祖先关闭小眼睛的有效状态仍进入整理输出并保持默认隐藏，普通隐藏残留才排除；图层样式总开关“效果”关闭时移除整组 `fx`，总开关开启时仅移除子项自身关闭的效果。已确认的 `_@` 运行时互斥状态可在整理稿中默认隐藏，不能按源隐藏内容删除；不为保留有效隐藏状态修改源 PSD；状态用途不明时列入 PSD 整理方案清单待确认，取舍写入原 PSD 修改说明。首次制作或批准重生成时逐组检查全部重复单元，按结构、字段和生命周期决定是否共用 Item；在 PSD 方案中确认 `_@` 模板的公共节点、状态专属节点、可替换内容及实例关系，并在 `_UI` 完成命名和结构整理。只改名任务保留原尺寸和结构，直接导出人工修正版不自动清理其隐藏层。
2. **导出前检查整理稿。** 检查人工修正、视觉、命名和导入约束。用户修正后的稿件作为续作输入；通用纠错可反馈到 Skill，单页选择记录在该界面说明中。
3. **使用现有工具导出视觉 Prefab。** 核对图片、字体、图层效果与引用。图片根据内容和导入设置判断复用，不能只看同名文件是否存在。调用前在第二份 MD 以 Importer、实际导入指纹、正式输出目标和关键配置检查排重，再建立或续记事件；编号不参与排重。图片确认与已有 Prefab 确认属于同一次导出，从排队到产物核验结束只调用一次生成入口。超时或状态不明只续记原事件并核验，不重发；同输入明确终结后再次导出仍需新请求。Prefab 正式生成后读取第三份 MD，只读盘点图片候选、大小图和共享引用，供减法判断；此时不执行资源改名、引用切换或清理。
4. **审核并落实适配范围。** 已有界面的当前资产和当前说明基线在导出前保存；同时保留刚生成且尚未后处理的视觉基线。正式 Prefab 导出后，基于实际节点、当前值、第二份 MD 和正式基线提交减法与适配审核；确认后再执行。每个字段最终采用生成值还是旧正式值由当前阶段对应的 MD 决定；只有跨阶段、存在关联字段或当前记录不足时才追加读取其他 MD。MD 未记录时先列差异并确认。后处理与最终刷新恢复后都审计相对生成基线的全部字段差异。
5. **完成减法与布局。** 保留需要的视觉和运行引用，按职责精简绑定，逐组核验已在 `_UI` 落实的 Item 模板及实例关系，不在 Prefab 阶段首次决定模板。普通内容区域默认以画布中心适配；货币、人物信息、导航栏等确实贴边的区域才按边缘或安全区定位，背景覆盖、布局组件驱动子节点及第二份 MD 已确认方案按各自职责处理。纯色黑色弹窗暗化层可按已确认方案不切大图，在 Prefab 使用铺满目标范围的内置 Image，Alpha 按源稿或用户确认值设置（70% 黑色覆盖对应 `0.7`），并核对层级与点击拦截；有纹理或渐变时不替换。已导出的旧大图须待 Prefab 解除引用并完成字段审计后，再按第三份 MD 核验和清理。逐文字节点核对实际字体、字号配置、颜色与透明度链、UGUI 组合对齐或 TMP 水平/垂直对齐字段、文字框、缩放链和最终显示；锚点居中不代表文字对齐居中。固定文本只检查现有文案，不额外做防爆框，动态文本才按实际预期处理长度、位数和换行带来的溢出风险。
6. **处理最终图片资源并完成绑定。** 减法和绑定前字段审计完成后，依据正式保留节点维护第三份 MD；存在改名、复用、引用切换或清理等可执行资源动作时，每项单独编号，经用户确认后通过 Coplay 执行并核验；没有可执行动作时只记录盘点结果，不提交空清单。图片资产名不强迫 PSD/Prefab 功能节点改名，也不因此重新导出 PSD→Prefab。先记录权威工具允许写入的组件与字段类别，再生成代码 → 修复清单内必要手写引用 → Unity 编译通过且类型可加载 → 刷新 Prefab 引用 → 回读图片引用并核对实际工具字段差异。
7. **维护已有功能并验证。** 新视觉节点承接已有业务时，按已确认清单补齐绑定、显隐和刷新，例如给现有选中状态接入新选中框；完全未实现的功能交给另一个 Skill。清单内代码无需二次确认，新发现的行为或作用域须补清单确认。功能代码完成后再次编译，再分别报告视觉、适配、编译、引用与运行检查的实际结果。

节点更名或类型变化造成的手写代码编译错误，在绑定刷新前处理；生成文件始终由工具维护。

## Skill 冲突处理

图片复用除“像素内容相同、仅尺寸不同则保留较大图”外，还允许宽高比不同的九宫格资源共用：以四角/边缘、可拉伸中心、Border/PPU 和所有目标尺寸的 `Sliced` 显示为证据，按覆盖能力选源。需要调整 Prefab Image Type 时走第二份 MD；资源切换与旧图清理仍须第三份 MD 确认及引用回读。

完整 Prefab 模式的减法审核须逐组核验 `_UI` 已落实的模板并确定参考样例最终去留；模板必要内容若遗漏，回 PSD 阶段确认和整理。核验通过后删除不参与运行的参考根；暂留、隐藏或改名不等于完成减法。第二份 MD 核销全部参考组且绑定前字段审计通过，才进入第三份 MD 正式资源动作和代码生成/绑定；用户修订只重验受影响项，不重审已批准且未变化的决定。已有界面默认只导图片的维护不进入此门槛。

执行本工作流时，其他 Skill（含项目 Skill）与本 Skill 冲突的流程要求以本 Skill 为准，其他资料仍用于核实真实工具入口与 API。工具输出沿用当前配置，不为固定目录要求改配置或搬资源；实际输出位置只核验和记录。用户明确指令仍优先。

## 两处审核与结果验收

首次制作和批准重生成的维护执行两处不同审核：生成/修改 `_UI` 前审核 **PSD 整理方案**；正式 Prefab 导出后，基于实际节点审核 **Prefab 减法与适配方案**。用户直接确认 PSD 方案且没有修改意见时，完成 `_UI` 和自检后直接导出，不再追加 PSD 结果验收；用户对 PSD 方案提出修改意见时，先落实到 `_UI` 并展示结果，用户针对结果回复“无修改”“没问题”“确认”等明确认可后直接导出，不再询问是否继续。导出后的 Prefab 审核只列减法、恢复、布局、工具生成和已有功能影响，不重复确认 PSD 动作。Prefab 清单也仅在用户提出修改意见时增加一次结果验收。`_UI` 输出指纹变化只用于产物核验，不触发 PSD 方案重审；Prefab 必须以实际导出结果建立本阶段清单。没有回复时等待。相关文件与 MD 出现未确认差异时先展示差异，确认后才能修改或同步记录；沿用 MD 中有效决策，不每次重新推导。审核中发现可复用经验时提出维护建议；只有用户明确授权后才可修改 Skill 或其他 `.aiworkflow/` 内容。详见 [两处审核](SKILL.md#当前迭代阶段的两处审核)。

## 已有界面如何维护

文字的阴影、描边和投影按同一类 Effect 需求核对；Prefab 只调整现有 UGUI `Outline` / `Shadow` 的 effect 属性，或目标项目已采用的 TMP `Modify Effect`。同类处理不代表现有 TMP 枚举可还原柔和投影；无法表达时记录视觉差异。非文字切图的开启效果仍在固定 `_UI` 中烘焙为最终像素。

本 Skill 不允许新增、复制材质或创建 Material Preset，也不允许隐式实例化材质；只复用现有材质，无法满足时记录差异。文字字号按节点对照固定 `_UI` 的有效字号/混合样式、实际字体与变换，以及刚生成 Prefab 的字体资源、`fontSize`、自动缩字和缩放链，最终以基准尺寸的实际字形显示验收；不使用全局换算比例，也不靠运行时代码补改字号。适配时也对照设计检查文字描边和阴影：UGUI Text 保留已有 Outline/Shadow，只调整其 effect 属性；目标项目已有并确认采用 Modify Effect 时，TMP 只调整该属性还原可表达的效果，否则按项目既有 TMP 方案与可用能力处理。任何路径都不新增材质、Material Preset、效果组件或脚本；缺少现成效果能力时记录差异。已有或已烘焙的效果不重复叠加，结果记录到同一份 Prefab 说明。

说明按阶段参与：PSD 整理及图层、固定 `_UI` 命名阶段读取并更新 `01-PSD修改说明.md`；Prefab 减法、布局、适配和绑定阶段读取并更新 `02-Prefab减法与布局说明.md`；工具导出后的 Unity 图片资源归纳、命名及清理阶段读取并更新 `03-图标归纳与命名说明.md`。只有跨阶段、存在关联字段或当前记录不足时才追加读取其他 MD，不能为了省略关联依据而只看单一记录。

迭代先读取当前阶段 MD 的有效执行依据；跨阶段、存在关联字段或记录不足时再追加读取其他 MD。复用成功路径，无新证据不重复已知失败方法；刷新后按相关 MD 恢复清单中明确的运行和视觉字段，再以刚生成视觉基线审计最终 Prefab。超时先核实真实产物；预览包含图像核验和明确清理入口，设计样例预览不代替真实运行数据验证。必要验证通过即结束。详见 [复用记录与减少返工](references/existing-ui-maintenance.md#复用记录与减少返工)。

完整 Prefab 模式的顺序（首次制作或批准重生成）：源稿与 `_UI` 对比 → 把差异纳入 PSD 整理方案并提交审核 → 用户审核同意 → 更新 `_UI` → 必要时完成 PSD 结果验收 → 原工具生成 Prefab 并保存视觉基线 → 只读盘点图片候选与共享引用 → 基于实际节点提交 Prefab 减法与适配审核 → 按确认清单和 MD 恢复并更新减法/适配 → 绑定前字段审计 → 有可执行资源动作时确认并执行第三份 MD 图片处理、无动作时只记录盘点 → 记录工具写入白名单 → 原工具生成代码 → 清单内引用修复 → 编译、刷新、集中恢复 → 回读图片引用 → 清单内已有功能适配 → 再次编译 → 最终 Prefab 字段审计 → 真实运行验证。此前没有实现的功能不自动补全；同一阶段、同一输入和同一清单不重复确认，但两处审核互不替代；有修改意见时仍须在对应产物完成后取得用户结果验收。

| 变化来源 | 处理方式 |
|---|---|
| 源 PSD 更新 | 对比新源、当前 `_UI` 和当前说明，把差异纳入 PSD 整理方案审核；用户同意后更新固定 `_UI`，保留可恢复基线。 |
| 人工修改 `_UI.psd` | 核验当前修正版后续作，不从源稿重新生成覆盖修正。 |
| 已有正式 Prefab 需要更新 | 默认 `Export Images` 后进入第三份 MD，核验现有引用与显示；整体大改先询问是否重生成，经批准才执行完整 Prefab、减法适配及绑定链。 |
| 用户已修改正式 Prefab 适配 | 读取 `02-Prefab减法与布局说明.md`，关联字段不足时再读取其他 MD；列出不一致，取得确认、更新 MD 后才成为新基线；纯适配变化不重导出、不重跑绑定。 |
| 只修改手写功能代码 | 核实现有节点与绑定仍满足需求后，直接修改并验证业务逻辑。 |

默认不复制新名字的 `_UI`、不要求临时候选再合并。生成前保留可恢复的旧资产及具体布局、组件和引用参数，核对工具覆盖范围；生成后检查 `.meta` / GUID、内部对象与外部引用，避免同路径但引用失效。共享图片变化需检查其他页面的引用影响。

本 Skill 禁止修改框架、共享运行基类、PSD 导入/导出及 UI 生成/绑定工具源码；手写代码只维护已明确的业务/UI 逻辑。疑似工具问题先核对固定 `_UI` 是否确有内容、实际导入路径与版本，再报告证据和阻断；不顺势修改工具。

## 固定的三份修改说明

每个界面固定维护三份权威 MD：`01-PSD修改说明.md`、`02-Prefab减法与布局说明.md`、`03-图标归纳与命名说明.md`。第三份专门记录导出图标归纳、历史遗留图标清理、用户确认、命名和引用核验。

文中历史遗留的“两份说明”仅表示前两份的职责分工；涉及 工具导出后的 Unity 图片资源、图标归纳、遗留清理或资源命名时，第三份说明是必读且必须同步维护的权威记录。PSD 图层及固定 `_UI` 命名只记录在第一份。

每个界面长期维护以下文件，各一份：

- `01-PSD修改说明.md`：源文件、整理稿、图层修改、人工修正、版本指纹及导出前检查。
- `02-Prefab减法与布局说明.md`：导出事件、正式改动清单、减法与布局依据、绑定执行、适配修订及验证。
- `03-图标归纳与命名说明.md`：导出图标归纳、历史遗留图标清理、用户确认、命名和引用核验。

新一轮源稿更新也在原文件内追加记录，用记录编号关联历史，不按轮次另建一套 MD。重生成前基线、工具输出、适配恢复与绑定完成状态分别标明；SHA-256 只用于识别版本，不能恢复旧文件或替代实际差异检查。

实际说明保存在目标项目允许的报告目录，位于 Unity 导入范围之外。本仓库仅保存通用模板。

## 只读检查脚本

脚本输出画布、图层层级、类型、可见性、文字和源文件 SHA-256，可选输出 PSD 内缓存的合成预览。它不修改 PSD、不重新合成图像，也不调用 Unity。

在已具备 Python 的环境中，可将依赖安装到本机外部缓存：

```powershell
$skillPath = '<项目/.aiworkflow/skills/plink-psd-to-unity-ui 的实际路径>'
$psdToolRoot = Join-Path $env:LOCALAPPDATA 'CodexTools/python-psd-tools'
python -m pip install --target $psdToolRoot -r (Join-Path $skillPath 'scripts/requirements.txt')

python (Join-Path $skillPath 'scripts/inspect_psd.py') '<输入PSD路径>' `
  --output '<新的图层报告.json>' `
  --preview '<新的预览.png>'
```

替换示例中的占位路径。输出父目录必须已存在，输出文件必须是新文件；已有可用依赖直接复用。脚本也支持 `--psd-tools-path` 指定依赖目录。缓存合成图可能陈旧，不能代替保存后视觉核验或 Unity 显示检查。

## 环境与验证范围

Coplay 默认由 Agent 自行发现、加载、连接并只读验证；连接异常自行排查恢复，不向用户追加连接不可用提醒或接入确认。PSD 盘点后继续提交整理方案，已有有效确认和 Photoshop 编辑能力时完成固定 `_UI` 整理与自检，不能仅交付盘点记录便结束完整制作。连接诊断写入当前阶段 MD，实际完成状态以调用和产物证据为准。具体规则见 [Coplay 连接故障处理](SKILL.md#coplay-连接故障处理)。

- 需要可保留 Photoshop 图层结构的编辑能力，以及项目现有的 Prefab 导出、代码绑定工具。本仓库不包含 Photoshop、Unity、PSUIResolver、XUGUI 或 Coplay。
- PLink 接入复用已有 PSUIResolver 与 XUGUI，Unity Editor 交互按项目要求使用 Coplay MCP。其他项目按实际工具和项目规则接入。
- PLink 的 Unity/Prefab/Assets 操作只能调用 Coplay MCP 的直接工具或请求载荷；禁止生成、保存、读取、传递或执行任何外部脚本文件作为 Unity 资源操作载体，也不得以脚本路径作为 Coplay 输入。PSD 编辑和烘焙可使用 Photoshop 或外部自动化，但不得绕过项目现成工具直接生成 Unity/Prefab 产物。Agent 默认自行接入、核验与恢复 Coplay，连接诊断不增加对话提醒或确认；导出写入只做只读诊断，不重试。图片模式在第三份 MD 追踪图片导出事件；Prefab 模式在第二份 MD 追踪图片与 Prefab 两道确认，同一图片输出范围跨模式也禁止并行/重复请求；同键事件未终结或结果不明时禁止第二次排队或调用导出入口。
- 不向 Unity `Assets` 新增流程辅助脚本或永久菜单；正常生成的绑定代码与明确要求的功能代码属于允许交付内容。
- 遵守目标项目规则和版本控制边界；本 Skill 不代替项目规范，也不自动执行 SVN 提交或其他版本调度。
- 当前版本已完成 Skill 结构、文档链接、场景推演和 PSD 像素烘焙流程记录。具体界面的 Editor 生成、编译、PlayMode 和设备适配仍按实际任务分别记录，不能互相替代，也不把未执行的验证写成已完成。

# PSD 整理与样例

本文任何旧的“两份 MD”表述只适用于 PSD/Prefab 字段；涉及 工具导出后的 Unity 图片资源归纳、改名、移动、引用切换、合并或清理时，必须读取并更新 `03-图标归纳与命名说明.md`；有可执行资源动作时须先取得第三份 MD 的用户确认，无动作时只记录盘点。PSD 图层及固定 `_UI` 命名只归第一份。

执行前遵守 [两处审核与结果验收](../SKILL.md#当前迭代阶段的两处审核) 和 [文件与 MD 一致性](../SKILL.md#文件与-md-一致性)：本阶段只审核 PSD 整理动作。用户未提出修改意见时，确认后完成 `_UI` 和 Agent 自检，按已确定模式直接导出，不增加 PSD 结果验收。用户提出修改意见时，先完成 `_UI` 并展示实际结果；用户对结果明确回复“无修改”等认可即为结果验收通过，随后直接导出，不再询问是否继续。只有完整 Prefab 模式在正式导出后另按实际节点提交减法与适配审核，该清单不重复 PSD 动作。只有已审核输入源 PSD/PSB 指纹变化，或用户明确扩展/替换已确认的 PSD 清单时，才重新审核 PSD 方案；保存 `_UI` 或生成 Prefab 的输出指纹变化不触发 PSD 重审。发现未确认的文件与记录差异，先展示并等用户确认，再补录基线或修改资产。

在分析、命名、调整画布或比较整理前后 PSD 时读取。

当前迭代阶段，首次整理、已审核输入源稿发生变化或用户明确扩展/替换已确认的 PSD 清单时，按 [两处审核](../SKILL.md#当前迭代阶段的两处审核) 提交 PSD 整理方案。用户对已展示的 `_UI` 结果提出返修意见时，只落实返修并重新展示结果验收，不重新提交原 PSD 方案；验收后直接导出。Prefab 正式生成后再基于实际节点提交独立的减法与适配清单。审核导致修订时，将可复用经验反馈到本 Skill 的 PSD 整理规则，原第一份说明记录该界面的实际修改及验证。下面的源更新差异对比作为该轮 PSD 方案审核的依据，不另设重复的 PSD 审批。

## 源更新先审核差异

源 PSD 更新时，先只读对比新源 PSD 与当前固定 `_UI`，结合原 `01-PSD修改说明.md` 的命名、分组、隐藏层处理和人工修正记录解释差异；可取得旧源版本时同时核对。不能把源与整理稿固有的加工差异全部认作新设计变化。把具体增删、视觉/文本/效果变化、拟保留修正及拟更新项写入当前说明，提交用户审核。用户同意本次差异后，才修改固定 `_UI` 并继续导出；一般性的“更新界面”请求不替代这次审核。已审核范围未变时后续不重复询问；源文件再次变化则复核新增差异。

用户只修改 `_UI` 并要求续作时仍按修正版检查入口执行，不误当成源更新。

## 源稿独立图层盘点

首次从源 PSD/PSB 整理为固定 `_UI`、或源稿更新需要重新转入内容时，在提交 PSD 整理方案之前，只读检查每个计划独立导出的非文字图片切图候选：单一图层，或由图层组、多层、剪贴/蒙版及效果形成的组合。逐目标记录源层/组定位与必要视觉链，分别查看组成层的非透明像素和目标切图在独立透明底合成后的像素、实际边界；核对主体、远离主体的孤立像素、异常大的边界及整页合成时被其他层遮住的内容。不能只看整页预览、单个子层、图层名称或源稿与整理稿的像素一致性；也不能为检查而合并源 PSD 或整页画面。结合蒙版、剪贴、已启用效果的合理外扩、合法背景及已确认的隐藏状态判断，不能把这些正常内容误作缺陷。

发现明显异常时立即告诉用户图层定位、独立图像证据、对合图或切图的影响和拟处理方式；长任务轮询中发现也当场报告，不等导出阶段或任务结束。把异常和待决定项写入第一份 MD，并作为同一次 PSD 整理方案的独立动作提交审核。处理方式未确认时，不自行裁边、擦除、合层或修改源稿，也不把异常图层转入可导出的 `_UI` 结果。确认后保留源 PSD 不变，只在已有可恢复备份的固定 `_UI` 中按确认范围修正；保存重开，逐目标核对独立透明底像素、边界和整稿显示，把结果写回第一份 MD。无法确认或验证的异常保持阻断，不能延到切图时首次处理。仅改名或直接使用人工修正版且不从源转入图层时，按任务范围核对实际使用稿，不擅自重做源稿整理。

## 源文件与输出命名

开始修改前记录本次输入 PSD/PSB 的路径和 SHA-256，完整保留源设计稿；后续整理只作用于当前约定的 `_UI` 工作稿。保存后再次计算源稿摘要，确认源文件没有被改写。文件指纹用于识别版本，不能替代可恢复的实际文件。

- 用户指定输出文件名时采用指定名称，并确保整理输出不覆盖源设计稿；未指定名称时采用用途后缀 `_UI`，例如 `BattleHUD.psd` → `BattleHUD_UI.psd`。PSB 沿用 `.psb`。
- 既有链条固定使用当前约定的 `_UI` 路径。新源稿更新时，完成上述差异审核后，先保留旧 `_UI` 的可恢复版本及原说明，再把新整理结果更新到该路径；不默认新增带时间戳的 `_UI` 作为另一份当前输入。备份位置遵守项目任务归档约定，并在原说明内关联。
- 目标已有文件时，先确认它是否属于本界面的整理链条；若是无关文件或目标与源设计稿实际为同一文件，先解决路径冲突，不能静默覆盖。用户直接提供 `_UI` 修正版时，以该保存稿续作；需进一步改写则先保留可恢复版本，只修改授权项，不重复追加 `_UI` 后缀。
- 同一轮继续保存和后续维护均使用已核实的当前工作稿。纯读取或直接使用已有稿生成 Prefab 时不制造额外 PSD。原稿与工作稿用途明确，不能让用户查看的固定 `_UI` 停在旧版，却把另一文件的导出结果作为交付。
- 文件名中的 `_UI` 只标识设计稿用途；Prefab 名、模块名、C# 类型名和导出路径单独按项目约定确定，不直接由 PSD 文件名追加后缀。

按 [阶段溯源记录](traceability.md) 建立或维护同一份固定的 `01-PSD修改说明.md`，新源稿只追加处理记录，不新增同类 MD。只记录变化项并写清原因，所有未执行的检查标为未执行；不能用模板的预期结果代替实际验证。

## 导出前整理稿检查

每次只导出图片、输出视觉 Prefab、临时 Prefab 或执行重导入验证前，检查本次实际使用的 PSD/PSB。该步骤是 Agent 的执行判断，不能替代修改意见触发的用户结果验收，也不表示已安装文件监听器或自动差异合并工具。

1. **核对输入与已记录版本。** 读取当前整理稿及原 `01-PSD修改说明.md`，核对路径、SHA-256、保存状态和已有结构/视觉证据；确认用户查看的当前 `_UI`、导入器实际输入与记录版本一致。指纹只能说明文件是否变化，不能识别作者、修改项或理由；不能只按文件名或时间戳选择版本。没有旧证据时检查当前稿，记录历史未知，不编造差异，也不只因缺少历史而阻止可验证的导出。
2. **识别实际修正。** 版本变化时，对照可用的旧记录、图层盘点和预览，检查命名、分组、层级/类型、Item 边界、图层增删、文字、位置尺寸、可见性及效果变化。以结构与视觉共同确认；解析工具未覆盖的属性需通过可靠编辑/预览通道检查。用户明确已修正时保留当前保存稿；与 MD 不一致的具体差异仍须列出并取得确认后才能作为本轮依据，不能只因已知作者而跳过确认。
3. **校验可导出性。** 检查本次画布约定、素材和字体、蒙版/效果、导入指令、切图路径冲突、绑定命名与 Item 作用域。对独立导出的非文字图片，复核第一份 MD 中源稿单层及组合候选的异常已按确认范围在固定 `_UI` 修正，并核对当前目标切图独立透明底合成像素、实际边界和整稿显示；人工修正版或整理后新增的异常也立即报告并记录。尚未确认或未通过重开核验的异常阻断包含该切图的导出请求，不在导出时首次决定如何修正源稿。非文字独立切图带已启用 `fx` 时，确认效果已按下节烘焙进目标像素；动态样式仍在而切图像素未包含效果，不算可导出。不要求修正版符合 Agent 上次的分组偏好；符合当前需求与工具约束就继续。发现会导致导出失败、引用冲突、关键视觉丢失或意图不明的问题时，列明具体图层、影响和建议，待用户决定后处理相关项，不自动改回旧规则。已有明确授权的修复无需重复确认。
4. **保留并记录。** 在原第一份说明追加人工修正、可核实的前后值、依据、当前指纹及本次检查结果；未知原因写“用户调整，原因未说明”。保留先前被导出使用的版本行。仅要求检查或记录时到此交付，不擅自生成 Prefab。首次缺少说明可建立首份并注明历史未知。
5. **从核验版本继续。** 按实际 PSD 路径和版本调用现有导出方法，核对导出前后输入指纹；期间文件又变化时不能把旧输出当作最新结果，先完成或裁决原导出事件，再核对新输入的授权和输出范围，按新事件导出。已有正式 Prefab 时，先按维护入口读取当前阶段对应 MD；跨阶段、存在关联字段或记录不足时再追加读取其他 MD。未记录或不一致项先列差异、确认并更新对应 MD。再保留取值证据、可恢复版本和引用身份，默认通过原工具仅导出图片并直接进入第三份 MD；只有首次制作或用户批准重生成时，才沿用完整主流程生成 Prefab。完整 Prefab 模式生成后先完成本轮减法与适配审核，再按确认清单和相关 MD 的当前有效记录恢复适配并完成绑定；同一 Prefab 输入、同一清单未变化时不重复本阶段审核，但不能用 PSD 授权、MD 旧记录或笼统完整流程授权跳过首次基于实际生成结果的 Prefab 审核。MD 不一致确认和修改意见触发的结果验收仍须完成；历史版本及旧导出记录保留，不回写成新结果。

源 PSD 的新一轮更新仍从源开始，但先只读核对上一版整理稿与原说明；发现尚未记录的修改时，先列差异待用户确认，再按可用证据补入原第一份，缺少旧证据则注明历史未知。参考这些修正，在新整理稿中保留仍适用的意图，不能用旧的生成或修正规则机械覆盖新设计。新源与旧修正冲突且无法判断时，只就具体冲突询问。先保留旧 `_UI.psd` 的可恢复版本，再更新当前约定路径，沿用上节规则。

### 反馈生成规则

- 可跨界面复用且有证据支持的生成错误，例如误判 Item 边界、产生非法绑定名，提炼为适用范围明确的 Skill 生成/检查规则，并记录依据与实际落点。不因一次页面修正就扩大成通用限制；规则改进不替代本轮修正版的保留和继续交付。
- 单页分组、命名选择、布局偏好和设计变化只维护该界面的原说明，下次处理该界面时参考，不写成所有 PSD 的默认规则。不把项目专有资源、API 或机器路径复制进通用规则。
- 按已有授权维护个人 Skill；只记录了建议但尚未修改规则时，明确标注“建议/未实施”，不能宣称规则已更新。原因不明确的人工修改先保留事实，不猜测并固化生成限制。

## 盘点脚本

`scripts/inspect_psd.py` 只读 PSD/PSB，输出 UTF-8 JSON。Python 命令和输入、输出路径由当前环境解析；从 Skill 根目录运行的通用示例：

```text
python scripts/inspect_psd.py <源PSD路径> --output <新的图层JSON路径> --preview <新的预览PNG路径>
```

Python 先使用当前环境的 `psd-tools`，或本机缓存 `%LOCALAPPDATA%/CodexTools/python-psd-tools/`；也可通过 `--psd-tools-path` 指定依赖目录。缺失时将 `scripts/requirements.txt` 中的依赖安装到本机缓存或项目允许的外部虚拟环境，不能把第三方包装进 Skill 或 Unity 工程。例如在 PowerShell 中，先将 `$pythonExe` 和 `$skillRoot` 设为当前环境核实的路径：

```powershell
$psdToolRoot = Join-Path $env:LOCALAPPDATA 'CodexTools/python-psd-tools'
& $pythonExe -m pip install --target $psdToolRoot -r (Join-Path $skillRoot 'scripts/requirements.txt')
```

只在依赖缺失或已确认不兼容时安装；已有可用环境直接复用。脚本不自动安装依赖、不写 PSD，也不调用 Photoshop/Unity。输出路径必须是新文件，避免覆盖已有报告或源资源。

预览来自 PSD 内保存的合成图，可能陈旧；它只用于辅助对照。没有合成图时不能把空白图当成预览成功。本次改写 PSD 时检查重新保存后的结构与真实合成结果；本次包含 Unity 交付时另检查 Unity 显示结果。已有整理稿可以只读核验，不为验收而强制重新保存。

## 图层操作映射

每个操作至少标明原图层定位、原名、目标路径、用途、操作和理由。图层 ID 可辅助匹配同一文件的前后版本，但不是跨文件的全局标识；缺失或重复时使用层级索引路径、类型、位置和视觉核对。重组会改变索引，必须基于操作前快照定位对象，避免边遍历边按已变化的索引改名。

| 原图层定位 | 目标路径 | 用途 | 操作 |
|---|---|---|---|
| 原稿中已确认的主背景层 | `bg` | 主背景 | 改名，保持比例 |
| 原稿中已确认的标志层 | `logo` | 标志 | 改名，保留透明边缘 |
| 原稿中的进度槽 | `progress/bg` | 进度条底图 | 分组并改名 |
| 原稿中的进度填充 | `progress/bar_c` | 代码控制的 Image | 分组并添加 XUGUI 组件标记 |
| 原稿中的说明文字 | `tips` | 静态文字 | 改名，保留文本属性 |

上表展示一个加载界面的整理模式；不是所有 PSD 都应该生成这五个元素。填充动画、时长和完成动作属于任务逻辑，不从这个样例继承。

## 尺寸与视觉

- 完整流程未另行指定时，目标画布为 750×1334；采用本次确认的目标尺寸同步调整设计坐标和必要的图层位置，不只修改文件名或 PNG 尺寸。用户只要求改名时保留原尺寸、坐标、分组及图层集合。
- 仅用于弹窗整体暗化、视觉上均匀纯黑半透明的遮罩层，可在已确认的 PSD 整理方案中标为不切大图，由 Prefab 阶段使用黑色、按源稿或用户确认不透明度配置 Alpha 的内置 Image 表达；70% 黑色覆盖对应 Alpha `0.7`。第一份 MD 记录源层及输出取舍。源稿不动；仅改名或直接导出人工修正版时不据此删除图层。纹理、渐变或特殊形状不可按纯色遮罩处理。
- 原稿与目标宽高比接近时，选择统一缩放系数并处理像素取整。比例明显不同时，等比缩放素材、调整画布和布局；不能为凑尺寸把 logo、人物、按钮或字体非等比拉伸。
- 超出画布的背景可能用于覆盖屏幕，不要按 PSD 画布边缘机械裁掉图层像素。记录背景延伸与关键内容可裁切范围。
- 保留文本可编辑性；字体缺失时核对项目字体映射及效果，不擅自栅格化文字或替换文案。
- 蒙版、图层样式、剪贴关系、智能对象和颜色配置会影响最终图像；重组之前先核对依赖，不能仅按矩形位置拼回一张看似相同的图。

## 命名与结构

- 用元素用途命名，禁止将所有图层机械音译或按序号重命名。静态装饰不必全部添加代码绑定后缀。
- PSD 导入指令与代码生成后缀属于两个协议：先核对导入器是否剥离 `/R`、`/SX`、`/SY`、`/T####` 等指令，再检查最终 Unity 节点名。不能因清理字符而破坏效果指令，也不能让指令进入 C# 字段名。
- 对代码绑定节点使用当前生成器支持的合法、唯一名称。PLink 的 `_c`、`_b`、`_g`、`_@` 详见 PLink 参考；其他项目不自动套用。
- 已知的一组成套切图在生成 `_UI` 时就命名，不延后到第三份 MD 才决定。例如白、蓝、紫、橙四档品质背景，先核对设计和实际数据字段的编号含义；一致时分别命名 `Quality_1`（白）、`Quality_2`（蓝）、`Quality_3`（紫）、`Quality_4`（橙），前缀按图片的真实用途替换。第一份 MD 逐图记录源层、颜色/档位、编号和目标切图层名；编号含义与表或现有有效记录冲突时先列差异确认，不仅凭图层排列猜测。相同语义的不同品质图使用同一前缀，不用 `Quality_c` 给某一档图片命名，也不把颜色词误当绑定后缀。
- 图片切图层名与运行时控件节点名是两个对象：`Quality_1` 等是导出图片的资源名；需要代码换图的 `Image` 控件才使用 `Quality_c` 或明确职责的 `QualityBackground_c` 等 `_c` 名。当前 PLink 导出器以非文字图层名同时生成 PNG 名和初始 Prefab 节点名，不能假定一个图层在一次导出中自动得到两套名称。首次完整生成时，按第二份 MD 的实际节点审核将最终保留的 Image 控件命名/绑定为 `_c`，其 Sprite 指向相应品质图片；仅导出图片的维护路径保留现有控件节点，只核验图片输出与 Sprite 引用。不得为图片改名机械修改控件，亦不得把四档素材当成四个运行时控件。
- `_UI.psd` 阶段只决定 PSD 图层的语义名称和导入指令；按本流程规则，PSD 转 `_UI` 的结果不得出现 `common` 图层名、资源名或目录名，也不创建或匹配 `common`。`common` 只允许在 工具导出后的 Unity 资源归纳阶段按对应规则处理。
- 使用功能分组保持进度槽/填充、按钮/文字等元素的相对关系，保持渲染顺序与蒙版关系。
- 不同父节点下同名的静态 `bg` 不一定是错误，但要检查图片导出是否按短名产生路径冲突；生成字段的重名还要按生成作用域单独检查。
- 整理输出前先识别运行时状态，再按下节处理关闭小眼睛的图层。小眼睛只表示当前展示，不单独证明图层无用；开启但被其他层遮挡、透明度为零或用途不明确的层，也不能仅凭这些现象删除。

### `_@` 模板与状态归纳

- PSD 为说明同一个 Item 而展示多个状态时，先盘点已确认有效的每套状态，包括源稿默认隐藏但运行时需要切换的状态，再总结一个 `_@` 模板所需结构。整理方案至少列出模板根、所有状态共有节点、各状态专属节点、图片/文字等可替换内容、默认状态，以及 PSD 中展示组与运行实例的对应关系。
- 多套状态展示用于还原模板的完整状态集合，不等于每套都要成为独立模板或常驻实例。说明哪些组只用于识别状态、哪些节点合并到模板、哪些实例需要保留；重复视觉在不丢失状态差异的前提下收敛到一个模板结构。
- 模板合并前形成运行时实体语义表：实例所属容器与数量、同一实体的互斥状态、公共与状态专属节点、一次写入的文本或图片字段、默认状态和状态切换入口，以及每个 PSD 参考组对应的运行时实体或状态。画面中的并列样例不能仅因视觉接近就判定为独立列表、独立模板或多个绑定字段。
- 将参考组迁入同一模板的互斥状态根时，以模板局部坐标的统一定位基准放置；不得继承参考样例为展示而存在的行列偏移。保存并重新打开 `_UI` 后，逐个核对互斥状态根的局部位置、尺寸、锚点和可见性，确认它们能在同一运行时位置切换。
- 先结合源稿的同级结构、画面内容、当前需求及已有设计/代码/MD，识别同一界面的互斥或条件显示状态；小眼睛和组名只是证据之一。源稿中自身或祖先关闭小眼睛的状态组，若能确认是运行时所需的另一状态，仍迁入 `_UI` 并保持默认隐藏，记录互斥对象、触发条件和切换入口；不能仅凭当前画面未显示就丢弃。无法判断其是否为有效状态时，在 PSD 整理方案清单列具体候选与依据等待确认，不擅自删除或把它当作已实现业务。普通隐藏残留仍按下节排除。
- 在生成或修改 `_UI` 前，将上述模板结构连同命名、状态切换边界和参考组取舍纳入 PSD 整理方案清单，取得用户明确确认后执行。无法从可见稿判定公共节点或状态归属时，列出具体冲突等待确认，不自行补全隐藏状态。下游 Prefab 动作在正式导出后基于实际节点另行审核。

### 隐藏图层排除

- 从源稿整理生成 `_UI.psd`（或对应 PSB）时，先逐组判断源隐藏内容是否属于同一界面已确认的运行时互斥/条件状态。属于有效状态的组及必要子层保留在 `_UI`，保持已确认的默认显隐，不能因祖先关闭小眼睛而遗漏整组。其余普通图层/组自身关闭或任意祖先关闭的内容应排除；不能因子层自身小眼睛开启而单独捞出。图层样式总开关和子效果关闭状态仍按下一条的三层效果规则处理。
- 在删除前逐项建立“源路径/ID → `_UI` 路径 → 处理理由”映射，并给源隐藏内容标明“有效运行时状态 / 普通隐藏残留 / 待确认”。只有已判为普通隐藏残留的内容才从输出排除；有效状态根保留并记录默认显隐、互斥对象及代码/绑定切换入口。盘点脚本的 `own_visible` 和 `effective_visible` 只说明当前 PSD 可见性，不能单独作为删除依据。
- 对仍需转移的源图层（包括已确认保留的隐藏状态），先检查图层样式总开关“效果”：总开关关闭时，子项名称和子项眼睛不改变“整组 `fx` 直接移除”的结论。总开关开启时，再检查 `fx` 子项；描边、投影等子项自身关闭时直接移除，只保留子项眼睛开启的效果。不得把关闭的总开关或关闭子项作为隐藏效果保留在 `_UI`。状态根默认隐藏不等于其内部开启的图层效果应被删除。
- 需要保留已确认的运行时隐藏状态时，不修改源 PSD 的小眼睛；只在 `_UI` 中保留其状态结构与默认显隐。其他源隐藏内容若被要求改为默认展示，先把意图纳入 PSD 整理方案清单并确认，再在 `_UI` 工作稿处理；源 PSD 仍保持不变。小眼睛开启但被遮挡、画布外或透明度为零，不属于本规则的隐藏判定。
- 这一步属于整理输出。仅改名任务仍不改变图层集合；直接核验或导出用户已修正的 `_UI.psd` 时不借本规则清理其文件，只有本次确实执行新一轮整理时才应用。不得将规则扩展为删除正式 Prefab 中的隐藏节点或 Item 模板。
- 透明度/填充烘焙、栅格化或局部合并必须以最新源隐藏内容已按映射处理、且模板默认隐藏状态已保留并核验的固定 `_UI` 为输入，不得回退到隐藏层取舍前的旧备份。确需从旧备份恢复 Fill/Opacity 时，必须先重新核对源映射及模板状态表，再继续烘焙；不能以隐藏图层数量为 0 作为验收条件。
- 在原 `01-PSD修改说明.md` 分别记录有效隐藏状态的保留依据、默认显隐和切换入口，以及普通隐藏残留的排除路径、自身/祖先隐藏原因及数量。保存后重新打开输出，核对保留状态及排除节点、效果取舍和源文件未变；必要时在工作稿临时切换状态检查视觉，复原默认显隐后保存。后续导出或 Prefab 后处理不得以旧资产、历史说明或相似节点重新补回已排除内容。隐藏判定不能替代这些视觉检查。

## 编辑与重新打开

优先使用当前可调用、能保留 Photoshop 结构的既有交互式编辑能力；PSD 的外部 Photoshop 自动化可作为编辑通道，但必须只改固定 `_UI` 工作稿、保留源 PSD 与可恢复备份，并按本节重新打开核验。命中需要编辑的锁定图层或组时，先在工作稿中记录原路径、锁定状态和解锁原因，再只解除该目标的锁定并完成已确认操作；保存后的输出保持解锁，不恢复锁定状态，除非用户明确要求重新锁定。不得为方便操作批量解锁无关节点。Unity/Prefab 资源的导出、改名、移动和绑定刷新仍只能使用 Coplay 的直接工具或请求载荷，不能由外部脚本代替。仅有只读解析库并不代表具备完整缩放/合成能力；没有可直接编辑通道时，交付图层盘点和操作映射并报告阻断。验证完成后只关闭本次打开的 PSD/PSB 文档页签：已保存的工作稿关闭时选择不再保存，只读检查稿同样不保存关闭；不得调用应用级退出、关闭 Photoshop 主窗口、影响用户已打开的其他标签或处理用户未保存工作。

## 填充与不透明度像素固化

准备转移到 `_UI` 的视觉图层，若自身或必要视觉链使用非默认 Fill（填充）或 Opacity（不透明度），在 `_UI` 工作副本中按以下顺序处理。Fill 与 Opacity 是两个独立属性，必须分别读取、记录和核对；不得把 Fill 改写成 Opacity，也不得只保留其中一个来代替另一个。

1. 保留源 PSD 和原始备份不变；在固定 `_UI` 工作副本中记录输入图层路径、Fill、Opacity、混合模式、剪贴/蒙版依赖及处理前合成预览。源图层的 Fill、Opacity 共同效果必须先保留，不能先把 Fill 改写为 Opacity。
2. 只隔离本节点及必要视觉依赖，确保目标层是 Pixel Layer；目标仍为 Shape/矢量层时先执行 Photoshop 的“栅格化”。不要把整个画布、整个组、源 PSD 或不相关节点合并进去。
3. 为每个目标 Pixel Layer 创建同级空白透明像素层，将目标层与该空白层合并。这个“建立透明像素层并合并”的动作就是最终烘焙步骤，用于把 Fill 与 Opacity 共同作用后的显示 alpha 真正写入像素；不得用把 Fill 改写成 Opacity 的方式替代。合并后保留目标原名、父组位置和层级关系。
4. 保存一个中间 PSD 后重新读取每个目标层，确认 `kind=pixel`、`Opacity=100%`、`Fill=100%`，并用 PSD 合成图逐像素比较处理中间结果与处理前备份；差异必须为空或有明确可解释的边界裁切差异。随后重新打开固定 `_UI` 做同样的结构、属性和合成复核。
5. 若 Photoshop 栅格化收紧透明边界，记录每个目标层的实际边界变化（例如原始 215×78 变为 212×76），并在后续切图/导出前重新核对图片尺寸、Prefab 几何和锚点。
6. 恢复或保留语义节点名称、所需层级/蒙版关系和绑定信息；记录固化前的 Fill、Opacity 与固化后的像素层状态。验收时允许固化层显示为 `Fill=100%`、`Opacity=100%`，但该结果只表示属性已烘焙进像素，不能作为把 Fill 替换成 Opacity 的操作依据。

不能安全确定局部合并范围、会破坏蒙版/混合效果，或无法重新读取验证时，停止该节点处理并在 `01-PSD修改说明.md` 记录阻断；不得把属性仍残留的“已栅格化”结果标记为完成。源 PSD 始终只读，所有编辑仅发生在 `_UI` 工作副本。

## 图片图层效果像素烘焙

PSD 中的阴影、描边、投影统一按 `fx`/Effect 效果识别并检查总开关与子项眼睛；“投影”不另建一套取舍流程。这里的非文字独立切图交付要求仍是把已启用效果烘焙成最终像素，文字则保留可编辑并走 Prefab 的现有 Effect 入口。

准备从固定 `_UI` 单独切出的图片、图标或背景，只要自身或必要视觉链带有已启用的描边、阴影等 `fx`，统一在调用导出器前把最终可见效果局部烘焙进目标像素并清除动态样式，不依赖导出器是否会处理图层效果。文字层仍保持可编辑，按 Prefab 文字效果规则处理。先完成隐藏层分类和效果总开关/子项眼睛取舍：已关闭的效果移除，不烘焙；只处理确认采用的开启效果。

1. 在不改源 PSD 的固定 `_UI` 工作副本中，逐个记录目标切图路径、已启用效果、Fill、Opacity、蒙版/剪贴及处理前的独立透明底渲染。先确认效果属于哪个切图节点；组样式跨多个切图或与邻层混合而无法局部归属时，列为阻断，不盖印整个画布或合并无关图层。
2. 隔离单个目标及必要视觉依赖，Shape/矢量层先变为 Pixel Layer。为目标层建立同级空白透明像素层并局部合并，使开启的描边/阴影与 Fill、Opacity 的共同显示一次写入像素；不能只执行“栅格化图层”而留下动态 `fx`，也不能先改 Fill/Opacity 数值再烘焙。与 [填充与不透明度像素固化](#填充与不透明度像素固化) 命中同一层时共用这一次合并，不重复烘焙。保留语义名称、父组、渲染顺序及必要绑定信息。
3. 保存中间稿并读回目标：`kind=pixel`、Fill/Opacity 均为 100%，目标层没有待导出的动态效果；独立显示在透明底上时，RGBA 像素、阴影/描边外扩边界及相对画布位置应与烘焙前一致。逐像素或等效图像对比无差异，允许的抗锯齿/色彩配置差异须逐项说明；整稿合成和其他节点也应保持不变。效果扩大或收紧透明边界时，记录图层矩形与偏移，导出前核对切图尺寸及后续 Prefab 几何/锚点。
4. 重新打开保存后的固定 `_UI` 重做结构、动态效果清除和独立图像核验，并在第一份 MD 记录 PSD 阶段结果。导出后再检查该节点实际 PNG 的透明边缘、效果范围及 Unity Sprite/Prefab 显示：PNG/Sprite 和图片模式的现有 Prefab 引用与显示记入第三份 MD；完整 Prefab 模式的生成后显示与布局另记入第二份 MD。PSD 整稿预览有阴影不能证明独立切图有阴影；未取得 PNG/Sprite 证据时只记录 PSD 阶段已完成，不宣称导出验收通过。

若透明层合并未真正消除动态样式、独立像素与原效果不一致或局部依赖无法保持，停止该图层导出，在第一份 MD 记录差异与阻断；不得改用手写 PNG、整稿盖印或修改导入器来掩盖缺失。

保存前后核对原稿摘要，重新打开输出并检查：画布、图层数量及映射、可见性、文字、图层效果和保存后的真实合成图。不能通过只改 PNG 或手写 Unity 层级来宣称 PSD 已完成整理。

当前环境没有可靠 PSD 编辑通道时，先交付图层盘点和可执行的操作映射，明确“PSD 尚未改写”的阻断；继续完成不依赖该改写的调查工作。不得把未执行的操作写成已完成。
